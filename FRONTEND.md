# Узел 12 — фронтенд диспетчера + мок-backend

Учебная модель. Не предназначена для управления реальным движением.

## Запуск (две консоли)

```bash
# 1. мок-backend (Python 3.11+)
cd mock_backend
pip install -r requirements.txt
uvicorn app.main:app --port 8000        # Swagger: http://127.0.0.1:8000/docs

# 2. фронтенд (Node 22 LTS)
cd frontend
npm ci
npm run dev                              # http://127.0.0.1:5173
```

Вход: `dispatcher/dispatcher`, `viewer/viewer`, `admin/admin` (демо-учётки мока).

Vite проксирует `/api`, `/health`, `/ws` на `http://127.0.0.1:8000`.
Чтобы подключиться к настоящему backend И, задайте `VITE_BACKEND=http://host:port npm run dev`.

## Что есть (P0)

- **Схема станции** (`frontend/src/station`, владелец Р): SVG 1400×900, 12 путей, горловины GW/GE, платформы,
  грузовой фронт, очередь у W, ресурсы L/B. Поезда движутся по `polyline` маршрута, прогресс считается по
  модельному времени (`started_at_s`/`expected_end_at_s`), в паузе и без связи не экстраполируется.
  Выбор поезда/пути/ресурса, масштаб колесом, перемещение мышью. Плановый маршрут — пунктир, факт — сплошной,
  вариант плана — фиолетовый пунктир. Закрытый путь — красный со штриховкой и подписью.
- **Панели диспетчера** (`frontend/src/{app,panels,timeline,api}`, владелец К): часы, запуск/пауза/×1/×5/×10/сброс,
  статус связи, внесение сбоя (закрытие пути, опоздание, недоступность локомотива), список конфликтов с подсветкой
  объектов на схеме, карточки объектов, индекс эффективности с вкладом факторов, сравнение двух вариантов плана,
  предпросмотр на схеме, принятие плана, диаграмма Ганта по путям, горловинам и ресурсам.
- Одно HTTP- и одно WebSocket-соединение; reconnect 1→2→4→8→10 с; при пропуске `ws_seq` или смене `run_id` —
  полный снимок; без связи команды блокируются, показывается время последнего обновления.

## Демо-страница без backend

```bash
cd frontend && node scripts/build-demo.mjs   # → dist-demo/uzel12-demo.html (один файл)
```

Сборка с `VITE_MOCK=1` подключает `frontend/src/mock/*` — порт мок-сервера на TypeScript, работает в браузере.
Используется для показа и как резерв на защите, если backend не поднялся. В обычной сборке не попадает в бандл.

## Мок-backend (`mock_backend/`)

Заглушка по контрактам ТЗ (разд. 6–7), чтобы фронт жил до готовности модулей В, И, Н.
Пошаговый симулятор (1 модельная секунда) исполняет принятый план с проверкой ресурсов;
жадный планировщик с ресурсными календарями (`passenger_first`, `earliest_departure`) и отдельным `validate_plan`.
Без PostgreSQL и аутентификации. Примеры данных — `shared/examples/*.json` (генерирует backend).

## ИИ-помощник

Работает сразу после входа в режиме **«Советы»**. Переключатель режимов — на правой панели и в верхней панели (клавиша **A**):

| Режим | Что делает |
|---|---|
| Выкл | ничего не анализирует |
| Советы (по умолчанию) | следит за станцией и пишет замечания; при конфликте или сбое сам заказывает расчёт и **рекомендует** лучший вариант — «Принять», «На схеме», «Сравнить», «Отклонить» |
| Автопилот | то же, но лучший допустимый вариант **принимает сам**; на 409 пересчитывает и повторяет до 3 раз |

Замечания (`computeTips` в `src/app/autopilotPolicy.ts`, только по данным снимка): поезд ждёт у W дольше 5 мин при
свободных подходящих путях; операция не может начаться дольше минуты; пассажирский опаздывает больше 5 мин;
все пути приёма грузовых заняты при подходе поездов; путь откроется или локомотив вернётся в ближайшие 2 мин;
индекс ниже «Нормы» — с главным фактором. Не больше 6, сначала важные.

Правило выбора варианта: все поезда размещены → меньше суммарная задержка → меньше переназначений (ТЗ разд. 14);
неполный и недопустимый план не рекомендуется и не принимается. Решения и рекомендации пишутся в журнал с причинами.
Работает в браузере, пока вкладка открыта; наблюдателю доступны только советы. Это правило поверх планировщика Н, а не обученная модель.

## Журнал событий и пакет сбоев

- Внизу вкладка «Журнал событий»: прибытия, приём на путь, отправления с опозданием, сбои, снятые конфликты,
  принятые планы и решения ИИ; фильтры, нажатие на событие выбирает поезд.
- В окне сбоя кнопка «В пакет»: несколько сбоев уходят одной командой (`batch`), сервер делает один пересчёт (ТЗ разд. 4).
- Тренд индекса за 15 минут под шкалой индекса (значения сервера).

## Работа с настоящим backend И

```bash
VITE_BACKEND=http://127.0.0.1:8000 npm run dev
```

`src/api/adapt.ts` приводит контракт И (ветка `backend`, `backend/app/domain/models.py`) к внутренним типам интерфейса:
геометрия путей из `snapshot.tracks`, `view_box/boundary_nodes/conflict_zones`, виды операций
(`dwell`, `shunt_to_*`), ресурсов (`locomotive`, `crew`, `cargo_front`), `wait_reason {code,message}`,
`severity error/warning`, объяснения-строки, неразмещённые операции, имена сбоев `delay_train`/`locomotive_unavailable`.
Если backend прислал только `active_plan_id` или `replan_finished.plan_ids`, планы читаются через `GET /api/plans/{id}`.

Пока у backend нет `/api/me` и `/ws` (этап 1), интерфейс входит без пароля как наблюдатель и читает снимок по HTTP
раз в 2 с (индикатор «Только HTTP»), команды заблокированы. Проверено вживую на ветке `backend` (commit 45bf1b8) с PostgreSQL 16.

## Отклонения от ТЗ / вопросы к И и Н

1. В `Snapshot` добавлены поля: `epoch`, `active_plan` (целиком), `conflicts`, `queue`, `index`, `incidents`;
   в `Train` — `forecast_departure_s`, `delay_s`, `actual_departure_s`, `wait_reason`, `current_operation_id`.
   Нужно для правой панели и диаграммы без пересчёта формул на фронте.
2. Устаревание плана проверяется по `epoch` (растёт при сбое/принятии плана/сбросе), а не по `state_version`:
   `state_version` меняется при каждой операции, и план устаревал бы через секунду при ×10.
   Дополнительно 409, если операции начались иначе, чем записано в плане.
3. `replan_finished` несёт сами планы в `payload.plans` (экономит запрос `GET /api/plans/{id}`).
4. Сбой автоматически запускает пересчёт (кнопка «Пересчитать» тоже есть).
5. Мок хранит пароли как sha256 с солью; у И — хеши из `*_PASSWORD_HASH`.
