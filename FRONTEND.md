# Узел 12 — фронтенд диспетчера + мок-backend

Учебная модель. Не предназначена для управления реальным движением.

## Запуск (две консоли)

```bash
# 1. мок-backend (Python 3.11+)
cd mock_backend
pip install -r requirements.txt
uvicorn app.main:app --port 8000        # Swagger: http://127.0.0.1:8000/docs

# 2. фронтенд (Node 22 LTS)
cd frontend
npm ci
npm run dev                              # http://127.0.0.1:5173
```

Vite проксирует `/api`, `/health`, `/ws` на `http://127.0.0.1:8000`.
Чтобы подключиться к настоящему backend И, задайте `VITE_BACKEND=http://host:port npm run dev`.

## Что есть (P0)

- **Схема станции** (`frontend/src/station`, владелец Р): SVG 1400×900, 12 путей, горловины GW/GE, платформы,
  грузовой фронт, очередь у W, ресурсы L/B. Поезда движутся по `polyline` маршрута, прогресс считается по
  модельному времени (`started_at_s`/`expected_end_at_s`), в паузе и без связи не экстраполируется.
  Выбор поезда/пути/ресурса, масштаб колесом, перемещение мышью. Плановый маршрут — пунктир, факт — сплошной,
  вариант плана — фиолетовый пунктир. Закрытый путь — красный со штриховкой и подписью.
- **Панели диспетчера** (`frontend/src/{app,panels,timeline,api}`, владелец К): часы, запуск/пауза/×1/×5/×10/сброс,
  статус связи, внесение сбоя (закрытие пути, опоздание, недоступность локомотива), список конфликтов с подсветкой
  объектов на схеме, карточки объектов, индекс эффективности с вкладом факторов, сравнение двух вариантов плана,
  предпросмотр на схеме, принятие плана, диаграмма Ганта по путям, горловинам и ресурсам.
- Одно HTTP- и одно WebSocket-соединение; reconnect 1→2→4→8→10 с; при пропуске `ws_seq` или смене `run_id` —
  полный снимок; без связи команды блокируются, показывается время последнего обновления.

## Мок-backend (`mock_backend/`)

Заглушка по контрактам ТЗ (разд. 6–7), чтобы фронт жил до готовности модулей В, И, Н.
Пошаговый симулятор (1 модельная секунда) исполняет принятый план с проверкой ресурсов;
жадный планировщик с ресурсными календарями (`passenger_first`, `earliest_departure`) и отдельным `validate_plan`.
Без PostgreSQL и аутентификации. Примеры данных — `shared/examples/*.json` (сгенерированы моком).

## Отклонения от ТЗ / вопросы к И и Н

1. В `Snapshot` добавлены поля: `epoch`, `active_plan` (целиком), `conflicts`, `queue`, `index`, `incidents`;
   в `Train` — `forecast_departure_s`, `delay_s`, `actual_departure_s`, `wait_reason`, `current_operation_id`.
   Нужно для правой панели и диаграммы без пересчёта формул на фронте.
2. Устаревание плана проверяется по `epoch` (растёт при сбое/принятии плана/сбросе), а не по `state_version`:
   `state_version` меняется при каждой операции, и план устаревал бы через секунду при ×10.
   Дополнительно 409, если операции начались иначе, чем записано в плане.
3. `replan_finished` несёт сами планы в `payload.plans` (экономит запрос `GET /api/plans/{id}`).
4. Сбой автоматически запускает пересчёт (кнопка «Пересчитать» тоже есть).
5. Роль выбирается в верхней панели (мок). Настоящий вход — `POST /api/login` (P1).
