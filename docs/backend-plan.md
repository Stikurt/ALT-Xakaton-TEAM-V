# Пошаговый план backend

Основание: ТЗ «Цифровая станция Узел 12», версия 1.0, разделы 5–7, 10, 16–18.
Роль пользователя соответствует участнику И. План относится только к backend.
Времена — ориентиры шестичасового командного хакатона, не обещание срока реализации.

| Этап | Ориентир по ТЗ | Ваши задачи | Результат / проверка |
|---|---|---|---|
| 1. Основа | 00:00–00:40 | FastAPI, модели, SQL, примеры, настройка БД | `/health`, `/docs`, сохранённый начальный снимок; контрактные тесты |
| 2. Одна общая станция | 00:40–01:30 | Подключить движок В, один управляющий цикл, GET state и WebSocket | Один поезд проходит цикл; UI получает факт и движение |
| 3. Надёжные команды | 01:30–02:30 | Очередь, версии, транзакции, идемпотентность, пауза/скорость/reset и сбои | Повтор command_id не меняет состояние; reset создаёт новый run_id |
| 4. Перепланирование | 02:30–03:30 | Процесс расчёта Н, API задач/планов, атомарное принятие | Закрытие пути → расчёт → принятие → исполнение; старый план даёт 409 |
| 5. История и отчёты | 03:30–04:30 | Снимки, replay, CSV, ошибки хранения | Последние 15 минут; экспорт совпадает с фактами выбранного run |
| 6. Доступ и устойчивость | 04:30–05:15 | Сессии, роли, настройки, reconnect, нагрузка | viewer получает 403 при изменении; 5 клиентов; результаты измерены |
| 7. Сдача | 05:15–06:00 | Запуск на ноутбуке команды, исправления, инструкция | Чистый старт, общий сценарий и доказанные результаты |

## Этап 1 — создан в этом изменении

1. Сохранить общие типы: секунды модели — целые, длина — метры, ID — строки.
2. Подготовить 7 таблиц предметных данных и таблицу результатов команд.
3. Сделать повторяемые миграции и безопасное начальное заполнение.
4. Дать К и Р исходный снимок и пример движения T01; Н — примеры Plan.
5. Проверить модели, ошибки HTTP, доступность документации и CORS.
6. На машине с PostgreSQL выполнить интеграционный тест и старт по README.

Пункты 1–5 выполнены локально. Пункт 6 требует реальной PostgreSQL; статус
зафиксирован в `tests/results.md`. Сам факт наличия SQL не означает успешную
интеграцию БД. План feasible в примерах иллюстрирует формат, а не доказательство
работы будущего общего валидатора.

## Этап 2 — реализован сценарий одного поезда

Подключены реальные В/Н, цикл команд/тиков, PostgreSQL checkpoint,
WebSocket, start/pause/speed/reset, восстановление в паузе, постоянные результаты
команд. Начальный план рассчитывается отдельным процессом CLI до старта сервера.
Часть инфраструктуры этапа 3 готова заранее, поскольку нужна для надёжной связи.
Полный многопоездный сценарий остаётся нерешённым: см. upstream-validation.md.
Ниже сохранён порядок интеграции и критерии этого этапа.

Вход от В: `create_initial_state`, `advance_to`, `apply_command`, `apply_plan`,
конфигурация и один исполняемый поезд. От Н: `can_start`, `validate_plan` и
допустимый план этого поезда. Предложенные сигнатуры уже в `domain/ports.py`.

1. Согласовать сигнатуры и ответы на вопросы из `decisions.md`.
2. Запустить единственный asyncio-цикл владельца состояния и монотонные часы.
3. Под общей блокировкой получать новое состояние и события от В.
4. Сохранить переход в короткой транзакции; только после commit заменить
   проекцию в памяти и отправить WebSocket.
5. При подключении отдавать snapshot с topology; затем state_updated и clock_sync.
6. Ограничить очередь каждого клиента; медленного отключать с восстановлением
   через новый snapshot, чтобы он не задерживал других.
7. Проверить: в паузе часы модели стоят, clock_sync идёт раз в секунду; T01 не
   телепортируется, seq и ws_seq не путаются.

## Этап 3 — команды и транзакции

`POST /api/simulation/control`, `POST /api/incidents`. В любой команде есть run_id
и command_id. Пара `(run_id, command_id)` хранит хеш запроса и итоговый ответ.
Повтор того же тела возвращает прежний результат; то же ID с другим телом — 409.
Проверка повтора должна происходить до проверки текущего run_id для повторного reset.
Эффект, события, снимок и ответ команды фиксируются одной транзакцией.

Часы сами по себе не меняют state_version. Существенное изменение повышает версию.
Ошибка БД останавливает модель, а не оставляет неподтверждённый факт в памяти.
start без допустимого принятого плана запрещён. Сбои проверяет В с правилами Н;
HTTP-обработчики не дублируют эти правила. Предусмотреть атомарный пакет сбоев
с одним последующим пересчётом.

## Этап 4 — расчёт и принятие

`POST /api/replans` → 202/job_id; `GET /api/plans/{id}`;
`POST /api/plans/{id}/apply`. Использовать отдельный процесс: один активный расчёт
и один последний ожидающий запрос. В расчёт передавать глубокую копию снимка.
Тайм-аут должен реально освобождать исполнитель, а не только прекращать ожидание.

При принятии под той же блокировкой проверить run_id, expected_state_version,
based_on_version, текущее sim_time_s и общий validate_plan. Время проверяется
отдельно: оно могло измениться без повышения версии. Записать событие и план;
В заменяет только будущие старты, сохраняя завершения уже начатых операций.
Два клиента не могут принять два плана на одну версию. partial не считается полным
допустимым решением. Ошибки расчёта уходят в replan_failed.

## Этап 5 — история

Снимок каждые 60 модельных секунд и при сбое/принятии плана. `GET /api/history`
восстанавливает состояние из снимка и событий до at_s, не меняя онлайн-модель.
Срок хранения по умолчанию 24 часа, доступны последние 15 минут.
`GET /api/export.csv`: поезд, плановое/фактическое отправление, задержка,
выполненные операции. Экранировать формулы электронных таблиц в текстовых ячейках.
Время отправления — достижение восточной границы, как в ТЗ.

## Этап 6 — доступ и проверка нагрузки

`POST /api/login`, серверные хеши паролей, защищённая cookie-сессия;
viewer/dispatcher/admin. Проверять сессию и Origin для WS, защищать cookie-команды
от CSRF. `PATCH /api/config` — admin, только в паузе, повышение версии и
устаревание вариантов. Секреты только из окружения.

Проверки A07/A08/A10/A11/A13/A14 — ваша основная зона. Остальные приёмочные
сценарии проверяются вместе с владельцами модулей. Нагрузка: 5 клиентов,
60 секунд, clock_sync 1 Гц и 10 команд всплеском. Отдельно измерять сервер,
получение в браузере и отрисовку; цель p95 <500 мс нельзя подтверждать одним
серверным таймером. Расчёт плана — отдельная цель до 5 с.
