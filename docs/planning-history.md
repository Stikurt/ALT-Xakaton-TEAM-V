# API планов и истории

## Запрос и результат

POST /api/replans принимает run_id и необязательный command_id. Для сетевого повтора
передавайте один и тот же command_id: ответ 202 `{command_id,run_id,job_id}` сохраняется
в одной транзакции с постановкой задачи. Инциденты создают задачу автоматически.

GET /api/replans/{job_id} возвращает job_id, run_id, based_on_version,
based_on_time_s, status, plan_ids, stale, identical, error. Статусы:
queued, running, completed, failed, superseded. Поставленная в очередь версия
уточняется в момент запуска расчёта по актуальному согласованному снимку владельца.
Новая ожидающая задача заменяет прежнюю; её job_id остаётся доступен со статусом
superseded. Одновременно выполняется один процесс и ожидает максимум одна задача.

После потери WS или обновления страницы GET /api/replans?run_id=... возвращает
последние 20 задач с plan_ids (limit от 1 до 50), чтобы восстановить результаты
без повторного расчёта. За применимостью варианта обращайтесь к GET конкретного плана.

Планировщик получает глубокую копию состояния, включая текущие назначения,
резервы путей и занятость конфликтных зон. Последовательно рассчитываются
passenger_first и earliest_departure. PLANNER_BUDGET_S=2 задаёт бюджет каждого
алгоритма; PLANNER_TIMEOUT_S=5 ограничивает весь процесс, включая запуск.
По жёсткому тайм-ауту процесс завершается и освобождается для следующего запроса.
PLANNER_TIMEOUT/PLANNER_ERROR уходят в сохранённый статус и replan_failed.

Результат с infeasible/partial остаётся результатом расчёта completed; принимать
его нельзя. Ошибка процесса — failed. Совпадение назначений обеих стратегий
помечается identical=true. Текущие факты и активный план во время расчёта не меняются.

## Просмотр и принятие

GET /api/plans/{plan_id} возвращает `{plan,stale,applicable}`. Plan включает
назначения, unassigned по операциям, показатели задержек, текстовые explanations,
violations общего валидатора и changes: `{operation_id,before,after}`.
Показатели описывают прогноз этого варианта; CSV содержит отдельно факты.

POST /api/plans/{plan_id}/apply:

```json
{
  "command_id": "new-unique-acceptance",
  "run_id": "current-run-id",
  "expected_state_version": 12
}
```

Владелец состояния проверяет run_id, expected_state_version, based_on_version,
полноту, время будущих стартов и настоящий RULES.validate_plan. После расчёта
время могло продвинуться без новой версии, поэтому версия не заменяет проверку
времени. Устаревание — 409 STALE_PLAN, недопустимость — 409 INVALID_PLAN.
Два принятия одной версии не могут оба изменить состояние. Повтор успешного
command_id возвращает сохранённый ответ; повтор отклонённого — тот же отказ.

В одной SQL-транзакции сохраняются plan_applied, accepted timestamp, состояние,
снимок и ответ; очищается потребность в новом плане. Только после commit меняется
онлайн-проекция и уходит WS. Движок заменяет будущие старты, сохраняет фактические
операции и события завершения уже выполняющихся. reset/принятие останавливают
ненужный активный процесс и отменяют ожидающую задачу.

Перезапуск помечает прерванный running как failed/PLANNER_INTERRUPTED и сохраняет
одну актуальную ожидающую задачу. Станция восстанавливается в паузе. Уже рассчитанные
варианты остаются в БД, но после смены версии могут быть устаревшими.

## История

GET /api/history?run_id=...&at_s=... возвращает StateResponse с дополнительными
view=history, read_only=true, at_s. Фронтенд показывает режим истории и не отправляет
управляющие команды из этого режима. Сам endpoint только читает PostgreSQL.

Снимки сохраняются каждую модельную минуту, при сбое/принятии плана, reset и ручном
запросе расчёта. События одного модельного момента несут итоговую динамическую
проекцию; историческое чтение выбирает ближайший снимок и последнюю следующую
проекцию событий до at_s в одном MVCC-снимке БД. Координатор разделяет длинный тик
по моментам событий и минутным границам. Между событиями меняется только sim_time_s;
Movement позволяет фронтенду интерполировать положение. События одного времени
показываются после обработки всей группы, команды этого времени — по последнему seq.

Будущий at_s даёт 409 HISTORY_IN_FUTURE. Неизвестный run_id — 404 RUN_NOT_FOUND.
Старые участки без достаточных сохранённых данных дают 409 HISTORY_UNAVAILABLE;
backend не восстанавливает их выдуманным расписанием. Reset архивирует предыдущий
run и сохраняет его checkpoint, планы, события и отчёт. Последние 15 минут и более
ранние сохранённые данные доступны; автоматическое удаление архивов отключено.

## CSV

GET /api/export.csv?run_id=... выгружает последнее сохранённое состояние выбранного
запуска. Параметр at_s ограничивает выгрузку тем же временем, что GET истории.
CSV — UTF-8 с BOM, разделитель запятая, стандартное экранирование кавычек.
Поля: run_id, at_s, train_id, scheduled_departure_s, actual_departure_s, delay_s,
completed_operations (ID через `;`). Фактическое отправление — завершение departure
у восточной границы. До него факт и задержка пустые. Задержка = max(0, факт − план).
Опасные начальные символы текстовых ячеек экранируются апострофом для таблиц.

## Ограничения проверки

Эти этапы проверяют работающий backend-сценарий T01 и настоящие модули Н/В.
Полные 15 поездов, сессии/роли и нагрузка браузеров не объявляются готовыми.
Архивы не удаляются автоматически: необратимое удаление требует отдельного разрешения.
