# Подключение модуля В

Это предложение локального интерфейса. На момент разработки общих `domain`-типов и кода
Н в репозитории не было. Доменные модели, API, хранилище и планировщик не изменены.
После публикации моделей И адаптирует JSON на границе; согласовать сигнатуры с И и Н.

## Публичные функции

Импорт: `from backend.app.simulation import ...` при запуске из корня репозитория.
При запуске backend из `backend` импорт будет `from app.simulation import ...`.

| Функция | Результат |
|---|---|
| `create_initial_state(config, run_id=None)` | `State`, пауза, исходный сценарий |
| `apply_plan(state, plan, rules=rules)` | `Transition` |
| `apply_command(state, command, rules=rules)` | `Transition` |
| `advance_to(state, target_s, rules=rules)` | `Transition`; в паузе время не меняется |
| `advance_elapsed(state, elapsed_s, rules=rules)` | `Transition`; реальный интервал умножается на speed |
| `snapshot(state)` | Независимый JSON-совместимый динамический снимок |
| `rules_context(state)` | Снимок, топология, текущие резервы и фактические назначения |
| `schedule_incidents(state, entries)` | Новое состояние для сценария/реплея; не HTTP API |

`Transition` содержит `state`, `events`, `result` и `replan_required`.
Входное состояние не изменяется, в том числе при исключении. И должен принять **возвращённое**
состояние, а не ожидать изменения переданного объекта. Не запускать несколько владельцев состояния.

`SimulationError` содержит `code`, `message`, `details`. Адаптер И отображает ошибки
неверного ввода в 422, устаревший план/запуск и несовместимое действие — в 409.
Ошибку самого валидатора нельзя скрывать: цикл приостанавливается и сообщает `simulation_error`.

## Сохранение и публикация — участник И

Одна блокировка охватывает чтение текущего состояния, вычисление перехода, сохранение и замену
live-state. Внешние вычисления планировщика выполняются отдельно; перед применением проверяется версия.

1. Получить `transition = apply_command(...)`, `apply_plan(...)` или `advance_elapsed(...)`.
2. В транзакции сохранить события, фактические операции, план и нужный снимок.
3. Добавить `recorded_at` по реальным серверным часам при записи. Движок выдаёт доменные события
   без этого поля, чтобы реальное время не влияло на повторяемость.
4. Только после commit установить `live_state = transition.state` и отправить сообщения WebSocket.
5. При неудачной записи не устанавливать новый state, остановить дальнейшее продвижение и
   показать ошибку сохранения; не отправлять неподтверждённые события.
6. Если `replan_required`, поставить **один** запрос расчёта для всего перехода. Движок сам
   не вызывает планировщик. Объединение ожидающих запросов выполняет И.

`seq`, `last_seq` и `event_id` в переходе предварительны до commit. `event_id = run_id:seq`.
При успешной записи номера должны сохраняться, а не назначаться ещё раз. Уникальности БД:
`(run_id,event_id)`, `(run_id,seq)`. `state_version` меняется на доменные события,
но не при одном продвижении часов. `ws_seq` назначает транспорт И, не движок.

Для `clock_sync` раз в реальную секунду достаточно `snapshot`, включая паузу.
И передаёт в `advance_elapsed` разницу **монотонных** часов. Перед сменой скорости/паузой сначала
учесть прошедший интервал на старой скорости; при паузе обновлять точку отсчёта, чтобы
время паузы не начислилось после возобновления.

`State` — внутренний объект с очередью, резервами, назначениям и кешем команд;
публичный `snapshot` не является полным checkpoint для восстановления движка.
Долговременный checkpoint/реплей после перезапуска сервера согласовать с И.
Встроенный кеш команд работает в памяти и сохраняет ответы через reset; И обеспечивает
его долговременное хранение/идемпотентность на уровне БД, включая применение плана.
Повтор успешной команды возвращает первоначальный `result` и пустой список событий.
Повтор command_id с другим телом отклоняется. Неуспешные команды в кеш не заносятся.

## Правила — участник Н

Передать объект с двумя методами:

```python
class RulesAdapter:
    def can_start(self, context, operation, assignment):
        # Вызвать общий валидатор Н, преобразовать результат в список конфликтов.
        # [] — разрешено. Непустой список — ожидание с причиной.
        raise NotImplementedError

    def validate_plan(self, context, plan):
        # Проверить полный план относительно текущего состояния и времени.
        # [] — допустим. Непустой список — запрет применения/запуска.
        raise NotImplementedError
```

Каждый конфликт обязан иметь `code` и `message`; остальные поля общего контракта можно добавить.
Контекст содержит `snapshot`, `topology` (полный config), `reservations` (`track_id → operation_id`),
`busy_zones` (`zone_id → operation_id`), `running_assignments` (`operation_id → assignment`).
Оба метода получают независимые копии, изменение аргументов не меняет состояние.

Назначения не сдвигаются молча: плановые поля остаются в `assignments`, фактические старты/концы
в `operations` и `running_assignments`. Если операция задержалась, фактический конец = фактический
старт + исходная длительность. Перед каждым стартом снова проверяются фактические ограничения.

`validate_plan` должен проверять не только статус `feasible`, но интервалы маршрутов/ресурсов,
удержание путей между операциями, предшественников, совместимость, ранний выезд, прибытия,
сбои и весь горизонт. Тестовая заглушка ничего из этого не доказывает.
Встроенные проверки движка защищают фактическое исполнение от наложений, но **не заменяют**
полную прогнозную валидацию Н.

При новом плане:
- `run_id` и `based_on_version` должны совпасть с текущим состоянием;
- только `feasible` с пустым `unassigned`; все pending-операции должны присутствовать;
- `start_s >= sim_time_s` для pending; интервалы положительные и длительность совпадает с операцией;
- running/completed можно не включать; если включены — назначение должно точно совпасть с сохранённым;
- завершения running остаются в очереди, удаляются только события будущих стартов старого плана;
- применить и затем вызвать следующий `advance_to/advance_elapsed`, чтобы начать назначения на текущем времени.

При `start`/возобновлении вызывается повторная `validate_plan` с текущим снимком.
Валидатор должен учитывать уже выполненные/выполняющиеся назначения и отличать их от будущих.

## Команды

```json
{"command_id":"cmd-1","run_id":"CURRENT_RUN","action":"start"}
```

Другие `action`: `pause`, `reset`, `speed` (поле `speed`: 1, 5, 10).
Один сбой:

```json
{"command_id":"cmd-2","run_id":"CURRENT_RUN","action":"incident","incident":{"kind":"close_track","target_id":"P04","duration_s":600}}
```

Другие виды: `delay_train` (`target_id`: поезд, `delay_s`: по умолчанию 300),
`locomotive_unavailable` (`target_id`: локомотив, `duration_s`: по умолчанию 600).
Пакет: `action="incidents"`, `incidents=[...]`. При одной недопустимой записи весь пакет отклоняется.
Порядок элементов пакета сохраняется; команды подаются последовательно через цикл И.
Форма HTTP из ТЗ преобразуется И в этот локальный формат.

Для заранее фиксированной временной последовательности:

```python
state = schedule_incidents(state, [
    {"id": "demo-close", "at_s": 600,
     "incident": {"kind": "close_track", "target_id": "P04", "duration_s": 600}}
])
```

Будущая команда проверяется в момент наступления; недопустимая создаёт `incident_rejected`.
На одинаковом времени сначала завершаются операции, затем сбои, прибытия и попытки стартов.
Внутри фазы стабильный порядок по ID; стартующие и уже ожидающие операции рассматриваются вместе по ID.
Пакет будущих сбоев вызывает один `replan_required` на возвращённый переход.

## Данные для Р

`movement = {route_id, started_at_s, expected_end_at_s}`.
Пока состав движется, `track_id` сохраняет исходный путь (при приёме это null),
целевой путь зарезервирован, но его `occupant_train_id` ещё null. После завершения
исходный путь освобождается и целевой получает поезд. Р рисует moving-поезд **только на маршруте**,
а не второй копией на исходном пути. После отправления `track_id=null`, статус `departed`.

Топология неизменяема: маршрут `polyline`, путь `geometry`, координаты условные, длина поезда — в метрах.
Снимок дополнительно содержит `conflicts`; это предложение расширения для согласования с И и К.
