# Готовое задание другой нейросети: авторизация и роли

Работай в репозитории https://github.com/Stikurt/ALT-Xakaton-TEAM-V.
Возьми актуальную ветку backend и создай от неё отдельную ветку feat/backend-auth.
Не меняй main и не загружай изменения напрямую в backend: там параллельно
продолжается реализация сбоев и перепланирования.

Нужно реализовать независимую часть этапа 6 — авторизацию и разграничение доступа
для FastAPI HTTP API и WebSocket. Вначале прочитай README.md, docs/backend-plan.md,
docs/contracts.md, docs/decisions.md, backend/app/main.py, api/live.py и settings.py.
Сохрани существующие контракты состояния, событий и команд.

## Результат

1. POST /api/login: username/password; роли viewer, dispatcher, admin.
   POST /api/logout завершает сессию; GET /api/me возвращает пользователя и роль.
2. Пароли проверяются на сервере по стойким хешам, без открытых паролей в коде.
   Используй ADMIN_PASSWORD_HASH, DISPATCHER_PASSWORD_HASH, SESSION_SECRET;
   добавь VIEWER_PASSWORD_HASH для отдельного viewer, поясни расширение ТЗ.
   Подготовь локальную команду генерации хеша с вводом пароля без отображения.
3. Оpaque случайная сессия хранится в cookie HttpOnly/SameSite; в БД хранится
   хеш токена, срок действия и роль. Выход и истечение срока реально отзывают доступ.
   Secure=true для HTTPS; явно настраиваемый режим локальной разработки HTTP.
   SESSION_SECRET и хеши не попадают в ответы, OpenAPI-примеры, логи и Git.
4. Без сессии API отдаёт 401; недостаточные права — 403. viewer читает состояние,
   dispatcher/admin управляют симуляцией. Для будущих настроек предоставь
   require_role('admin'), но не реализуй чужую логику изменения конфигурации.
5. /ws также проверяет сессию и разрешённый Origin до accept. Истёкшая или отозванная
   сессия не должна оставлять бессрочно авторизованное открытое соединение.
6. Cookie-команды защищены от CSRF: проверка Origin и отдельный CSRF-токен,
   который frontend отправляет в заголовке. CORS использует точный список origin,
   credentials=true и необходимые заголовки, без '*'. /health остаётся публичным.
7. Сохрани формат ошибок {code,message,details}. Не меняй run_id, command_id,
   state_version, идемпотентность или последовательность исполнения команд.
8. Тесты: неверный пароль; вход и выход; истечение/отзыв сессии; 401/403;
   viewer не может менять скорость/start/reset; dispatcher может; admin-role
   dependency; WS без сессии/с чужим Origin; CSRF; отсутствие секретов в ответах.
   Уже существующие тесты адаптируй к авторизации через тестовую сессию, не удаляй
   их, не ослабляй и не помечай skipped ради зелёного результата.

## Границы изменений

Основные новые файлы: backend/app/auth/, tests/test_auth.py, docs/auth.md и новая
SQL-миграция. Номер миграции проверь по актуальной базе ветки — не перезаписывай
существующие миграции. Минимально допустимы изменения main.py, settings.py,
api/live.py для подключения защиты, .env.example и фиксированных зависимостей.
Не переписывай runtime/coordinator.py, simulation, planner, constraints, историю
или расчёт планов. Не добавляй второй сервер, frontend, SQLite, регистрацию
пользователей или внешнего провайдера входа.

Учитывай, что backend развивается параллельно: перед завершением сравни изменения
с актуальной backend и опиши возможные точки конфликта. Не выполняй force push
и не объединяй ветки без отдельного поручения.

В конце верни коммит/ветку, список изменённых файлов, инструкцию генерации хешей,
пример входа и защищённой команды для frontend, точные результаты запущенных
проверок и ограничения. Если PostgreSQL не был доступен, явно отличай тесты с
двойником хранилища от настоящего интеграционного прогона.
