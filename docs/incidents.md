# Инциденты: контракт для фронтенда

Текущий run_id берите из GET /api/state. Новый command_id создавайте для каждого
нового действия; при сетевом повторе используйте то же тело и ID.

## Одиночный запрос

POST /api/incidents, Content-Type: application/json:

```json
{
  "command_id": "unique-command-1",
  "run_id": "replace-with-current-run",
  "kind": "close_track",
  "target_id": "P04",
  "duration_s": 600
}
```

| kind | Цель | Обязательное время | Ограничение движка |
|---|---|---|---|
| delay_train | T01 и другие поезда | delay_s | Только статус scheduled |
| close_track | P01–P12 | duration_s | Нельзя, если уже идёт входящее движение |
| locomotive_unavailable | L01/L02 | duration_s | Локомотив должен быть свободен |

Время — положительные целые модельные секунды. Опоздание прибавляется к
expected_arrival_s. Недоступность начинается в момент обработки команды; повторное
закрытие с новым ID не сокращает уже установленный срок. Занятый поездом путь
можно закрыть для новых входов, если на него нет начатого входящего движения.
Движок сам восстанавливает доступность по истечении срока.

## Пакет

POST /api/incidents/batch:

```json
{
  "command_id": "unique-batch-1",
  "run_id": "replace-with-current-run",
  "incidents": [
    {"kind": "close_track", "target_id": "P04", "duration_s": 600},
    {"kind": "locomotive_unavailable", "target_id": "L01", "duration_s": 300}
  ]
}
```

Допустимы 1–50 элементов. Порядок сохраняется. Движок проверяет пакет на копии
состояния: отказ любого элемента отменяет весь пакет. Успех даёт по событию
incident_applied на элемент, один ответ и одну ожидающую заявку перепланирования.
Версия повышается по числу существенных событий, а не всегда ровно на 1 за HTTP.

## Ответ и повторы

HTTP 200: `{command_id,run_id,state_version,replan_required}`. События, состояние,
checkpoint, заявка и ответ фиксируются одной транзакцией PostgreSQL. Обновление
WebSocket публикуется после commit. GET state и первый snapshot нового WS
показывают replan_required. Дубликат не создаёт событий и не публикует обновление.

HTTP 409: INCIDENT_REJECTED, STALE_RUN или COMMAND_ID_REUSED. Отказ движка для
известного запуска сохраняется: повтор вернёт прежнюю ошибку даже после устранения
причины. Изменённое тело с прежним ID также даёт 409. Для новой попытки нужен новый ID.
Неизвестный запуск не имеет строки runs, поэтому его отказ не кэшируется.

HTTP 422: неверные поля, типы или размер пакета; такие запросы не попадают в очередь
и не сохраняются. HTTP 401: нет сессии. HTTP 403: роль ниже dispatcher, неверный
CSRF-токен или запрещённый Origin (`docs/auth.md`). HTTP 503: недоступная модель/хранилище
или заполненная очередь. Единый формат ошибки: `{code,message,details:[]}`.

## Граница этапа

replan_requests хранит одну последнюю потребность на run_id, а не готовый план
и не факт запуска расчёта. Новые инциденты заменяют её версию/seq; reset удаляет
заявку старого запуска. Перезапуск backend восстанавливает признак из таблицы.
Сообщения replan_started/finished/failed появятся с исполнителем этапа 4.
Авторизация и роли этапа 6 описаны в `docs/auth.md`.
