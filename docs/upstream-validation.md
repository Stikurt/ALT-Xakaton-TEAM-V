Реальный planner + RULES + engine на one_train.json дают feasible без нарушений.
T01 проходит приём, стоянку и отправление к модельной секунде 600. API и WebSocket

## Одна точечная правка общего валидатора

В constraints.validate_plan блок проверки непрерывности движения повторно
рассматривал уже running/completed операции как будущие. При паузе в момент 60 с
и последующем start для T01 возникало ложное «Повторный приём поезда на путь».
Перед обходом будущей цепочки добавлен фильтр operation.status == pending.
Существующий учёт текущей позиции и назначения running сохранён, как и проверки
ресурсов, маршрутов, длительностей и предшественников. Проверки паузы/возобновления
в 60, 120 и 500 секунд выполняются с настоящим RULES.
Эту маленькую правку следует передать в ветку Н при следующем объединении.

## Нерешённая задача полного сценария

Исходный общий тест test_real_station_planner_and_simulation_contract из
командной интеграционной ветки был выполнен локально и упал: planner вернул
infeasible для shared/station.json. В unassigned есть местные поезда, включая
T03/T06, с причиной TRACK_OCCUPIED; валидатор также сообщает о недостающих
будущих операциях. Поэтому backend не принимает такой вариант и не заявляет
готовность 15 поездов. Падение зафиксировано, а не исправлено подменой статуса.

В текущий набор backend включены модульные тесты участников и собственная
интеграционная проверка одного поезда. Известно падающий общий тест 15 поездов
не включён: это незавершённая контрольная точка следующего этапа, а не passed.

Для повторения причины на актуальных модулях:

```python
import json
from pathlib import Path
from app.simulation import create_initial_state, snapshot
from app.planner import plan
config = json.loads(Path('shared/station.json').read_text(encoding='utf-8'))
candidate = plan(snapshot(create_initial_state(config)), config, 'passenger_first', 4.0)
print(candidate['status'], candidate['unassigned'], candidate['violations'])
```
