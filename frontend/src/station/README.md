# StationView — модуль участника Р

Первая рабочая версия интерактивной схемы по ТЗ «Цифровая станция Узел 12», разделы 2, 6, 8 и 12. Все изменения изолированы в `frontend/src/station`. В репозитории при начале работы был только пустой `README.md.txt`, поэтому здесь же размещён временный стенд для проверки графики. Это не второй frontend продукта: после появления общей оболочки участник К импортирует компонент, а стенд остаётся инструментом разработки.

## Что готово

- SVG 1400×900; 12 путей из `geometry`, платформы, грузовая зона, западная и восточная горловины.
- Поезда из фактического снимка; интерполяция по длине `polyline`, ограничение прогресса 0–1 и указатель направления.
- Свободные, занятые, закрытые пути; штриховка и подпись закрытия, отметка ожидания и подсветка конфликтов.
- Выбор пути/поезда мышью, Enter или пробелом; очередь у W; отправленные и ещё не прибывшие поезда на путях не рисуются.
- Масштаб 100–333%, перемещение перетаскиванием, кнопка возврата ко всей станции.
- Пауза, скорости ×1/×5/×10, остановка в истории и при потере связи; серверное время имеет приоритет.
- Пунктирный прогноз маршрутов и будущих назначений без добавления фиктивных поездов. Чужой `run_id` скрывает наложение; несовпадающая версия помечает прогноз устаревшим.
- CSS ограничен классом `.sv`. Компонент не открывает WebSocket, не выполняет API-команды и не рассчитывает допустимость плана.

## Запуск стенда

Нужны Node.js 22.12+ или 24 LTS и pnpm. Проверено на Node.js 24.19.0, pnpm 11.19.0 в Windows.

Из корня репозитория:

```powershell
cd frontend/src/station
pnpm install --frozen-lockfile
pnpm build
pnpm preview
```

Открыть http://127.0.0.1:5173. Для обычной локальной разработки предусмотрен `pnpm dev`. В ограниченной среде Codex его оптимизатор зависимостей получил отказ доступа к корню диска; проверенный здесь способ — `build` + `preview`.

`pnpm test` — шесть тестов геометрии и часов. `pnpm test:browser` — браузерная проверка при запущенном стенде. По умолчанию используется установленный Microsoft Edge. Для Chrome задайте `BROWSER_CHANNEL=chrome`; адрес можно переопределить через `TEST_URL`. Playwright сохраняет снимки в игнорируемую Git папку `test-results`.

## Подключение к оболочке участника К

```tsx
import { StationView } from './station';
import type { Selection } from './station';

<StationView
  snapshot={snapshot}
  topology={topology}
  selection={selection}
  onSelect={setSelection}
  previewPlan={previewPlan}
  viewMode={historyMode ? 'history' : 'live'}
  connection={connected ? 'connected' : 'disconnected'}
  clockReceivedAtMs={clockReceivedAtMs}
  conflicts={conflicts}
  highlightedEntityIds={focusedConflict?.entity_ids ?? []}
/>
```

`onSelect` возвращает `{ kind: 'train' | 'track', id: string }` или `null`. Родитель отвечает за карточку выбранного объекта. В стенде карточка демонстрационная; она не заменяет панель К.

При **каждом** `snapshot`, `state_updated` и `clock_sync` родитель атомарно обновляет время/скорость/паузу и `clockReceivedAtMs = performance.now()`. Не использовать `Date.now()`: это другая шкала времени. Не привязывать часы к `state_version`, поскольку `clock_sync` её не изменяет. Изменение скорости должно поступать с актуальным `sim_time_s`.

При отключении передать `connection='disconnected'`: схема показывает последнее подтверждённое `sim_time_s`, а не продолжает локальное движение. После восстановления сначала получить согласованный снимок и новую отметку получения. В истории передать исторический снимок и `viewMode='history'`. При reset заменить `run_id` и весь снимок; компонент не хранит собственных состояний поездов.

Если `conflicts` содержит несколько конфликтов, выделяются все их объекты. Чтобы показать только выбранный конфликт, передать его `entity_ids` в `highlightedEntityIds`, а `conflicts` опустить.

Для интеграции нужны `StationView.tsx`, `station.css`, `geometry.ts`, `types.ts` и `index.ts`. `demo`, `tests`, локальные `package.json`, lock-файл и настройки относятся только к стенду; их не нужно подключать в production App. У модуля нет иных runtime-зависимостей, кроме React.

## Допущения, которые нужно согласовать с И и В

Общие схемы ещё не опубликованы. `types.ts` — временный контракт представления, а не новая серверная схема. Когда появятся OpenAPI/shared-типы, заменить эти определения импортами или явно согласованным адаптером.

- `geometry` и `polyline` приняты как массивы `[x, y]`, так как ТЗ не задаёт конкретный JSON-формат координат.
- `Topology` содержит статические `tracks` и `routes`; `snapshot.tracks` — динамические доступность/занятость по тем же ID. Дополнительные поля backend допускаются структурной типизацией.
- Коды типов путей и поездов зафиксированы в `types.ts`; их нужно сверить с backend.
- `connection`, `clockReceivedAtMs`, `conflicts` и `highlightedEntityIds` дополняют пять базовых props из ТЗ для корректной анимации и подсветки.
- Поля задержек, ресурсов и подробного плана карточки принадлежат общей панели. Стенд не выдумывает прогноз задержки и показывает «Нет данных».

## Границы демонстрации и оставшаяся интеграция

`demo/fixtures.ts` содержит **визуальные тестовые снимки**, а не допустимый начальный план всей станции. Некоторые составы специально уже стоят на путях на отметке 60 с, чтобы одновременно проверить разные состояния. T01 демонстрирует приём 0–120 с, стоянку до 480 с и отправление до 600 с. Локальные часы стенда нужны только для подачи тестовых props.

До командной приёмки необходимо подключить реальные snapshot/topology, проверить согласованные типы и прогнать A01, A09, A11 с backend и общей оболочкой. Нагрузочное требование p95 <500 мс и работа пяти клиентов здесь не проверялись. Текущий результат — готовый к интеграции модуль схемы, не завершённая система управления станцией.
